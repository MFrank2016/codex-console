# codex-console 统一代理调度与动态代理升级 Phase A 设计

- 日期：2026-03-25
- 状态：Approved-for-planning
- 目标读者：产品负责人、实施开发者、项目维护者
- 当前仓库：`/root/code-server/workspace/codex-console`

## 1. 背景

当前项目已经同时存在三类代理来源：

1. 请求显式传入的 `proxy`
2. 动态代理接口
3. 本地代理列表 / 全局静态代理

但这些来源目前没有统一调度层，导致实际行为分散在多个入口中：

1. `src/core/dynamic_proxy.py` 里的 `get_proxy_url_for_task()` 只支持“动态代理失败后回退到静态代理”。
2. `src/web/routes/accounts.py` 的 `_get_proxy()` 又额外插入了一套“代理列表优先”的本地逻辑。
3. 注册单任务、普通批量、无限批量、Outlook 批量等链路虽然都支持 `proxy` 字段，但没有共享的失败切换和批量代理池策略。
4. 动态代理设置页仍停留在“GET 一个代理字符串”的简化模型，不支持：
   - POST 请求
   - curl 解析
   - 批量代理列表返回
   - 结构化对象映射
   - 按任务大类配置默认探测地址 / 请求数量 / 分配策略

用户本轮希望先完成 Phase A：**建立统一代理调度层，并把动态代理配置能力升级到可支撑单任务 fallback 与批量代理池策略的程度**。

本设计不追求一次性做完所有代理管理交互，而是优先解决“谁来统一选代理、怎么切代理、批量任务怎么安全使用动态代理池”这三个架构问题。

## 2. 已确认范围与决策

### 2.1 本轮属于 Phase A

本轮只覆盖：

1. 统一代理调度层
2. 动态代理配置模型升级
3. 设置页动态代理面板升级
4. 所有当前调用 `get_proxy_url_for_task()` 的入口切换到统一调度

### 2.2 本轮不属于 Phase B

以下内容明确不在本轮实现范围内：

1. 代理列表服务端分页
2. 代理导入结果弹窗
3. 代理检测弹窗（含“检测勾选项 / 检测全部 / 自定义目标地址”完整交互）
4. 代理池持久化与进程恢复
5. 多实例共享代理租约

### 2.3 用户已确认的核心规则

#### 调度总优先级

1. 请求显式传入的 `proxy` 优先级最高，直接直通
2. 非批量任务：动态代理池 → 代理列表 → 静态代理
3. 批量任务：只走动态代理池；动态代理池不可用时直接失败，不回退到代理列表/静态代理

#### 批量动态代理池

1. 在批量任务开始前预抓动态代理
2. 预抓规模：`并发数 × 3`，上限 `100`
3. 预抓后必须先做连通性测试，筛掉不可用代理
4. 可用代理数量不足以满足所选策略时，直接阻止批量开始
5. 运行中代理池耗尽时，剩余任务直接失败，不降级、不补抓
6. 代理池运行态只放内存，不做数据库持久化恢复

#### 批量代理分配策略

需要支持：

1. `exclusive`：所有正在进行的任务不使用重复代理
2. `consume_once`：整个批次生命周期内代理不重复使用
3. `strict_isolation`：优先按出口 IP 去重；若拿不到出口 IP，则退化为按代理字符串去重
4. `random`：随机选取

#### 单任务 / 非批量任务

1. 动态代理请求数量做成可配置项
2. 从动态代理回退到本地代理列表时，使用启用代理随机候选
3. 本地代理候选上限默认为 `5`
4. 代理相关失败判定为：
   - 网络层错误
   - 代理链路错误
   - 风控 / 封禁特征（如 `403`、`429`、captcha / blocked / access denied）

#### 动态代理配置面

1. 支持 `GET` / `POST`
2. 支持解析 curl 请求并自动识别常见鉴权信息
3. 同时保留原始 header/body 请求模板
4. 动态代理接口返回只要求支持**批量代理列表**
5. 返回格式支持：
   - 字符串列表
   - 结构化对象列表
6. 结构化对象字段映射采用：
   - 自动识别常见键名
   - 允许手工覆盖映射
7. 检测目标地址按**任务大类**配置默认值，并允许请求参数覆盖
8. 先按任务大类配置，数据模型预留以后扩展到更细粒度

## 3. 现状诊断

### 3.1 代理选择逻辑分散

当前代理相关逻辑分散在：

1. `src/core/dynamic_proxy.py`
2. `src/web/routes/accounts.py`
3. 注册 route / service 调用链

问题是：

1. 不同入口的优先级不一致
2. 失败后如何切换代理没有统一规则
3. 批量任务没有成型的代理池抽象

### 3.2 动态代理模型过于简化

当前只支持：

1. 单个 URL
2. 可选 API key header
3. 可选 result field

这不足以支持：

1. curl 转配置
2. POST body
3. 批量请求数量
4. 批量返回列表
5. 对象数组字段映射

### 3.3 批量任务缺少受控代理池

当前批量注册虽然能传 `proxy`，但没有统一的：

1. 预抓
2. 探测
3. 可用池筛选
4. 独占/消费/隔离策略
5. 运行中耗尽处理

这意味着一旦把“批量动态代理”直接塞进现有逻辑，极易变成大量散落的边界判断。

## 4. 目标与非目标

### 4.1 目标

Phase A 必须达成以下目标：

1. 建立统一代理调度入口，覆盖所有当前调用 `get_proxy_url_for_task()` 的入口。
2. 明确显式 `proxy`、动态代理、本地代理列表、静态代理之间的职责边界与优先级。
3. 为批量任务建立内存态动态代理池，支持四种分配策略。
4. 统一单任务与非批量任务的 fallback 语义和代理相关失败判定。
5. 把动态代理设置从“单 URL + 单结果”升级为“结构化请求模板 + 结构化列表解析 + 按任务大类默认配置”。
6. 保持当前技术栈不变，不引入新的基础设施前置条件。

### 4.2 非目标

本轮不包含：

1. 代理列表分页与重做管理表格
2. 代理检测弹窗与完整代理管理页交互重构
3. 动态代理池数据库持久化
4. 进程重启恢复
5. 多实例共享代理租约
6. 每个业务入口自定义一套独立失败 DSL

## 5. 推荐方案与理由

本轮采用已确认方案：**集中式统一代理调度服务层**。

### 5.1 为什么不用“调用点各自补逻辑”

如果继续在 `registration.py`、`accounts.py`、`registration_service.py` 等调用点单独补判断：

1. 规则会再次分散
2. 批量策略会被迫侵入多个文件
3. 以后继续扩展 Phase B 时很难保持一致

### 5.2 为什么不用“重型代理任务子系统”

如果直接上持久化代理池、租约恢复、多实例一致性：

1. 范围明显超出本轮
2. 需要更多模型和迁移
3. 会显著放大验证与回归成本

### 5.3 方案结论

因此本轮采用：

1. **动态代理基础设施层**：负责请求模板、curl 解析、返回解析、连通性探测、出口 IP 探测
2. **统一代理调度层**：负责单任务 fallback 与批量代理池策略
3. **设置与配置层升级**：负责保存动态代理源配置和按任务大类默认配置
4. **调用入口层接入**：所有现有调用点只向统一调度层拿代理

## 6. 架构边界与核心组件

### 6.1 分层结构

建议新增如下逻辑分层：

1. **动态代理底层能力层**
   - 负责：请求构造、curl 解析、返回解析、代理项标准化、探测
2. **统一代理调度层**

3. **设置与配置层**
   - 负责：读取/保存动态代理源配置与任务大类默认配置
4. **调用入口层**
   - 负责：声明当前任务属于哪类场景，并调用统一调度层，不再自行拼接选择逻辑

## 8. 动态代理请求与解析模型

### 8.1 curl 解析

设置页允许用户粘贴 curl，请前端解析后生成标准化配置：

1. method
2. url
3. headers
4. body
5. 常见鉴权字段

后端不负责完整 shell 级解析，只负责接收标准化配置。

### 8.2 返回格式

动态代理返回支持两种模式：

1. **字符串列表**
   - 例：`["http://u:p@1.2.3.4:8080", ...]`
2. **对象列表**
   - 例：`[{"host": "...", "port": 8080, "username": "...", "password": "...", "type": "http"}]`

### 8.3 对象字段映射

对象列表解析采用：

1. 自动识别常见键名：
   - `host/ip/server/address`
   - `port`
   - `username/user`
   - `password/pass`
   - `type/protocol/scheme`
2. 允许手工覆盖映射

### 8.4 标准化代理项

无论来自字符串列表还是对象列表，都要转换成统一内部模型，至少包含：

1. `proxy_url`
2. `scheme`
3. `host`
4. `port`
5. `username`
6. `password`
7. `source_metadata`

## 9. 运行时数据流

### 9.1 单任务 / 非批量任务

统一流程如下：

1. 若请求显式传入 `proxy`，直接使用，不进入统一调度 fallback。
2. 否则根据任务大类读取默认配置。
3. 向动态代理源请求 `N` 个候选代理。
4. 对候选代理做连通性测试，并按需获取出口 IP。
5. 若存在可用动态代理候选，则按顺序尝试。
6. 若动态候选耗尽，再从本地启用代理中随机挑选候选，数量上限默认 `5`。
7. 本地代理候选耗尽后，再回退到静态代理。
8. 若静态代理仍失败，则任务失败。

### 9.2 批量任务

统一流程如下：

1. 批量开始前读取任务大类默认配置。
2. 根据 `并发数 × 3`，并限制最大 `100`，计算预抓规模。
3. 向动态代理源请求候选列表。
4. 对候选执行连通性测试，并尽量获取出口 IP。
5. 根据策略整理批量代理池。
6. 若可用数量不足以满足策略要求，则直接阻止批量开始。
7. 批量开始后，每个子任务启动前由代理池分配一个代理。
8. 子任务结束后，根据策略决定是否释放、消费或标记已使用。
9. 若运行中代理池耗尽，则剩余任务直接失败，不降级、不补抓。

### 9.3 四种策略语义

#### `random`

1. 从可用池随机选择
2. 允许复用

#### `exclusive`

1. 所有正在运行中的任务不允许重复代理
2. 任务结束后代理可重新回池

#### `consume_once`

1. 一个代理只要被分配过，就不再复用
2. 不区分成功或失败

#### `strict_isolation`

1. 优先按出口 IP 去重
2. 若拿不到出口 IP，则退化为按代理字符串去重
3. 一旦被占用或消费，不再重复使用

## 10. 失败判定与回退规则

### 10.1 代理相关失败

本轮采用共享内置判定器，不做任务级 DSL。以下情况视为代理相关失败：

1. 网络层异常：
   - 连接失败
   - 超时
   - 代理认证失败
   - TLS / 握手失败
   - DNS / socket 类错误
2. 明确的代理链路状态码：
   - `407`
   - `502`
   - `503`
3. 风控 / 封禁特征：
   - `403`
   - `429`
   - 含 `captcha`、`blocked`、`access denied`、`forbidden` 等特征文本

### 10.2 回退边界

#### 单任务 / 非批量

允许按如下链路切换：

1. 动态代理候选之间切换
2. 动态代理耗尽后切换到本地代理列表候选
3. 本地代理列表耗尽后切换到静态代理

#### 批量任务

不允许回退到：

1. 本地代理列表
2. 静态代理
3. 新一轮动态补抓

批量任务一旦动态代理池不满足规则，只允许：

1. 启动前失败
2. 运行中耗尽后剩余任务失败

## 14. 风险与控制

### 14.1 风险：入口接入不一致

如果仍保留入口自行选代理，很容易再次分叉。

**控制：**

1. 明确统一调度服务为唯一入口
2. 以测试锁死旧入口行为迁移

### 14.2 风险：动态代理配置面过大

如果一次性暴露过多高级字段，设置页会迅速复杂化。

**控制：**

1. 默认表单只露出核心字段
2. 复杂 header/body/映射通过折叠高级区展示

### 14.3 风险：批量策略语义混淆

`exclusive`、`consume_once`、`strict_isolation` 很容易被实现成近似但不一致的行为。

**控制：**

1. 独立批量代理池抽象
2. 每种策略单独测试
3. 用日志字段记录实际分配来源和策略

---

## 15. 结论

Phase A 的核心不是继续在现有调用点补零散判断，而是建立一个**集中式统一代理调度层**，并把动态代理升级为可描述“批量列表获取 + 探测 + 分配策略”的基础设施。

在该设计下：

1. 单任务与非批量任务将获得清晰的 fallback 链；
2. 批量任务将拥有受控的内存态动态代理池；
3. 设置页将能够描述真实可用的动态代理请求模型；
4. Phase B 才有基础继续推进代理列表分页、检测弹窗和管理页交互增强。
