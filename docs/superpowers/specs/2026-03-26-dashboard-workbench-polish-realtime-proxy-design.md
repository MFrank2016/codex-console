# Dashboard、注册工作台样式增强与代理策略设计

- 日期：2026-03-26
- 状态：Approved-for-planning
- 目标读者：产品负责人、实施开发者、项目维护者
- 当前仓库：`codex-console`
- 前置基础：`2026-03-25-dashboard-and-registration-realtime-event-stream-design.md` 已落地主干能力

## 1. 背景

上一轮已经完成两项关键工作：

1. 首页 `/` 已升级为 Dashboard 样式。
2. 注册工作台 `/registration-workbench` 已切换到统一实时事件流主链路。

但用户在继续使用后又明确提出了 7 类新问题：

1. Dashboard 当前层级还不够强，每个总览卡片都需要更明确的背景色。
2. 统计数字还不够醒目，希望每个核心数字有不同的强调底色。
3. 快捷动作目前更像链接块，希望改成按钮化交互。
4. 侧边栏缩放按钮位置和折叠态体验不好，希望按钮跟侧边栏本体融合，折叠后只展示图标。
5. 注册工作台实时日志区希望更高，并与左侧配置区在视觉上接近齐平。
6. 用户体感上仍然认为“实时日志没有实时展示”，要求彻查并修复，而不是只改显示样式。
7. 注册任务要增加“是否使用代理”选项，并统一代理来源优先级规则。

这意味着本轮不再是“纯样式润色”，而是一次 **视觉强化 + 实时链路核查修复 + 代理选择策略统一** 的组合迭代。

---

## 2. 本轮确认结果

经过本轮澄清，用户已经明确确认：

1. **整体视觉基线**：采用 **B 方案（浅色高亮控制台）**。
2. **代理开关位置**：放在 **配置区**，而不是高级自动操作区。
3. **代理开关适用范围**：覆盖所有任务类型：
   - 单次注册
   - 普通批量
   - 无限注册
   - Outlook 批量
4. **静态代理定义**：指当前表单中已有的手动/固定代理配置。
5. **单任务反馈方式**：不再以步骤列表作为主视图，而改为 **进度条模式**。
6. **无可用代理时的失败策略**：按 **任务创建后立即失败** 处理，并在任务状态与实时日志中明确展示失败原因。

---

## 3. 本轮目标与非目标

### 3.1 目标

本轮必须完成以下目标：

1. 强化 Dashboard 视觉层级，使其更像高亮控制台而不是基础容器。
2. 将快捷动作改造成清晰的按钮组交互。
3. 修复工作区侧边栏折叠后的布局与交互问题。
4. 提升注册工作台日志面板的可视高度与观察效率。
5. 将单任务反馈卡改成“进度条 + 当前步骤 + 总耗时”的模式。
6. 对“实时日志仍不实时”的问题做根因级排查与修复。
7. 为所有任务类型增加“是否使用代理”选项，并统一代理优先级决策。
8. 在无可用代理时，让任务创建后立即失败，并且错误对用户可见、可追踪。

### 3.2 非目标

本轮不包含：

1. 推翻上一轮统一实时事件流架构。
2. 重做 Dashboard 数据来源或引入新的图表系统。
3. 引入新的前端框架（React/Vue）或全量设计系统。
4. 对所有页面同步做视觉统一升级；本轮只覆盖 Dashboard、工作区壳层、注册工作台。
5. 改动无关业务流程（账号管理、定时任务、支付等）。

---

## 4. 整体设计结论

### 4.1 推荐方案

本轮采用 **平衡增强方案**：

1. 视觉上，围绕现有 Dashboard / Registration Workbench 结构做强化，而不是推倒重来。
2. 实时日志问题按 **根因修复** 处理，继续使用已有 stream snapshot / events 架构。
3. 代理逻辑统一收口到后端单点决策函数，不把优先级判断散落到前端和多个 service 中。

### 4.2 设计原则

1. **先增强结构，再增强装饰**：先保证按钮、卡片、侧边栏、日志面板结构合理，再上色彩与质感。
2. **实时问题不做表层补丁**：任何“看起来实时”的修复，都必须证明主链路确实不再依赖 DB flush。
3. **代理决策单点收口**：所有任务类型共用一套代理来源优先级，避免行为不一致。
4. **错误必须可见**：无代理可用时，不允许静默回退或悄悄无代理执行，必须明确失败。

## 5. Dashboard 视觉设计

### 5.1 总体风格

Dashboard 采用 **浅色高亮控制台** 风格：

1. 页面整体以浅背景和柔和阴影为主。
2. 每张卡片都有独立背景色/渐变背景，而不是统一灰白容器。
3. 统计数字用彩色标签底块强调，颜色之间承担“信息分组”作用。

### 5.2 指标卡设计

四类指标卡建议保持一一对应的固定色：

1. 注册任务：蓝色系
2. 成功率：紫色系
3. 账号：绿色系
4. 定时计划：橙色/琥珀色系

视觉结构：

1. 卡片本体使用浅色背景块或轻渐变背景。
2. 指标 label 使用较弱色值。
3. 指标 value 外层用高饱和色底块（圆角标签或胶囊块）强化可扫读性。
4. hint 文本保留，但降低视觉噪音。

### 5.3 最近活动与快捷动作

最近活动区：

1. 保留列表结构。
2. 每一项有浅色 item 背景。
3. 状态标记使用胶囊标签样式，而不是裸文本。

快捷动作区：

1. 改为 **按钮组**，不再只是整块链接卡。
2. 设定主次层级：
   - 主按钮：去注册工作台
   - 次按钮：账号管理、定时任务、系统设置
3. 主按钮色彩更高亮，次按钮采用柔和浅色块。

## 6. 工作区壳层与侧边栏设计

### 6.1 问题定义

当前侧边栏主要问题有：

1. 折叠按钮与内容区关系不自然。
2. 折叠后样式错位，视觉上像“浮在页面上”。
3. 折叠态没有完全切换成图标导航。

### 6.2 目标状态

本轮侧边栏需要达到：

1. 折叠按钮与主题按钮都归入侧边栏本体，而不是漂浮到页面头部主区域。
2. 展开态显示：图标 + 文字。
3. 折叠态显示：仅图标。
4. 折叠后内容区宽度、左边距和按钮位置一起协同变化。
5. 当前激活页面在折叠态仍有明显高亮。

### 6.3 结构建议

1. 侧边栏头部区域包含：
   - 品牌/标题
   - 折叠按钮
2. 侧边栏主体区域为导航图标 + 标签。
3. 侧边栏底部区域放主题按钮。
4. 折叠态时：
   - 标题隐藏或缩写
   - 导航文字隐藏
   - 图标居中
   - theme/toggle 按钮与导航宽度保持一致

## 7. 注册工作台视觉与反馈设计

### 7.1 布局

继续保留上一轮确认的：

- 左侧配置区约 1/3
- 右侧反馈区约 2/3

本轮仅做强化，不改总体布局方向。

### 7.2 单任务反馈卡：改成进度条模式

单任务反馈卡不再以“步骤列表”作为主视图，而改为固定的进度摘要卡。

卡片需要展示：

1. 当前步骤名（例如 `submit_login_email`）
2. 当前步骤序号 / 总步骤数（例如 `第 4 / 10 步`）
3. 当前整体耗时（例如 `02:14`）
4. 整体进度条

为了保证“第几步 / 总步数”在所有恢复路径中都能稳定计算，本轮需要同时明确数据契约：

1. 单任务 `snapshot` 必须能够稳定提供总步骤信息。
2. 可接受的实现方式有两种，但最终计划里必须只选一种并统一：
   - `steps` 始终为全量步骤列表
   - 或额外提供 `step_index` / `total_steps`（或等价字段）
3. `task_step_updated` 增量事件也必须提供可直接渲染当前进度的字段，不能依赖前端从“最近步骤”中猜测。

交互语义：

1. 进度按步骤数推进，而不是做时间估算型假动画。
2. 当前步骤进行中时，进度条停留在当前步骤对应位置。
3. 若任务失败：
   - 保留当前步骤位置
   - 状态切为失败
   - 详细失败原因交给日志区承载

### 7.3 批任务反馈卡

继续保留：

1. 目标数
2. 成功数
3. 失败数
4. 进度条

同时对视觉层级做增强：

1. 目标数使用浅蓝背景
2. 成功数使用浅绿背景
3. 失败数使用浅红背景
4. 进度百分比或状态使用浅黄/中性背景

### 7.4 日志面板高度

本轮需要显著拉高日志面板：

1. 让日志区高度与左侧配置区在视觉上更接近齐平。
2. 减少用户频繁滚动日志面板的需求。
3. 保持长日志场景下滚动区独立，不挤压顶部任务卡。

建议：

1. 反馈区使用三段式布局：
   - 单任务卡
   - 批任务卡
   - 日志区（占剩余高度）
2. 日志卡最小高度应明显高于当前版本。

## 8. 实时日志问题的根因排查与修复设计

### 8.1 当前风险判断

虽然上一轮已经将主链路迁移到统一 stream 事件流，但用户仍反馈“实时日志还是没有实时展示”，说明至少存在以下可能性之一：

1. 某些关键路径仍然在 UI 上依赖旧的 `/logs` 或旧 detail 刷新逻辑。
2. reducer / render 层虽然接收到了 `log_appended`，但没有立即刷新日志窗口。
3. WebSocket 断线或页面切换后，fallback 路径没有按 seq 及时补回增量事件。
4. 某些任务类型（例如 Outlook 批量）仍然沿用了旧日志追加路径。
5. 后端 runtime 在某些步骤只更新了状态，没有发出对应日志事件。

### 8.2 本轮修复原则

本轮必须先完成 **根因调查**，再实施修复。调查和修复必须满足：

1. 明确区分“事件没发出”和“事件发出了但 UI 没渲染”。
2. 明确区分“单任务”和“批任务/Outlook 批量”路径。
3. 明确区分“WebSocket 在线”和“fallback 恢复”路径。

### 8.3 修复目标

修复完成后，注册工作台日志必须满足：

1. 首屏通过 snapshot 建立日志上下文。
2. 增量日志通过 `log_appended` 实时追加。
3. 断线恢复时通过 `/registration/streams/*` 的 snapshot/events 补偿。
4. 工作台主路径不再依赖 DB flush 结果来驱动“实时日志显示”。
5. 单任务、普通批量、无限注册、Outlook 批量的日志展示行为一致。

## 9. 代理开关与代理决策设计

### 9.1 表单设计

注册配置区新增：

- **是否使用代理**（布尔开关）

该字段放在基础配置区，与邮箱服务、注册模式、流水线等基础参数同级。

### 9.2 适用范围

统一适用于：

1. 单次注册
2. 普通批量
3. 无限注册
4. Outlook 批量

### 9.3 代理决策规则

当“是否使用代理 = 关”：

- 任务按无代理执行。

当“是否使用代理 = 开”：

按以下优先级依次决策：

1. **动态代理**
   - 如果当前系统已启用动态代理，则优先使用动态代理。
   - 即使表单中同时配置了静态代理，也不得覆盖动态代理优先级。
2. **代理列表**
   - 若未启用动态代理，则尝试从代理列表中获取可用代理。
3. **静态代理**
   - 若代理列表无可用代理，则尝试表单中的静态/固定代理配置。
4. **失败**
   - 如果上述三类来源都不可用，则任务创建后立即失败。

### 9.4 失败语义

本轮用户明确要求：

- **创建任务后立即失败**，而不是提交前拦截弹窗。

因此设计上要求：

1. 任务对象仍然创建成功，便于追踪。
2. 任务进入失败状态，失败原因明确写入：
   - 任务状态
   - 实时日志
   - 必要的错误提示文案
3. 不允许默默降级为“无代理执行”。

推荐失败文案示例：

- `代理已启用，但动态代理未开启、代理列表为空且静态代理未配置，任务终止。`

### 9.5 后端收口方式

代理来源决策必须在后端单点收口，不能在多个页面 handler / route / service 中重复拼接规则。

建议新增统一 helper / policy：

- 输入：
  - `use_proxy`
  - `dynamic_proxy_enabled`
  - 代理列表状态
  - 静态代理配置
- 输出：
  - `proxy_mode`: `none | dynamic | pool | static | failed`
  - `proxy_value`
  - `error_message`

这样可以保证所有任务类型行为一致，也方便测试。

## 10. 测试设计

本轮至少需要补齐以下测试：

### 10.1 Dashboard / 样式资产测试

1. Dashboard 模板仍包含关键挂点。
2. Dashboard 样式文件包含卡片背景与按钮样式选择器。
3. 快捷动作渲染输出符合按钮化结构。

### 10.2 侧边栏交互测试

1. 折叠态 body class 切换正确。
2. 折叠后导航仅展示图标。
3. 折叠按钮与主题按钮的位置仍然可用。

### 10.3 单任务进度卡测试

1. 根据步骤总数和当前步骤正确渲染进度比。
2. 能正确显示“第几步 / 总步数”。
3. 能正确显示整体耗时。
4. 失败时保持当前步位置和失败状态。

### 10.4 实时日志测试

1. `snapshot` 正确建立日志首屏。
2. `log_appended` 正确追加，不重复、不漏行。
3. fallback events 路由在 DB 未 flush 前也能返回 live log。
4. WebSocket / polling / snapshot_required 三条链路行为一致。
5. Outlook 批量也能实时看到日志追加。

### 10.5 代理策略测试

1. `use_proxy = false` 时明确无代理。
2. `use_proxy = true` 且动态代理开启时优先使用动态代理。
3. 动态代理不可用时回退代理列表。
4. 代理列表为空时回退静态代理。
5. 三者都不可用时创建任务后立即失败。
6. 单次/普通批量/无限/Outlook 批量行为一致。

## 11. 风险与控制

### 11.1 风险

1. 样式增强可能影响现有侧边栏和工作区共享布局。
2. 单任务反馈卡改版可能破坏现有步骤列表相关测试。
3. “日志仍不实时”的真实原因可能在多条链路叠加，不一定是单点 bug。
4. 代理策略统一后，某些旧入口可能暴露出之前被掩盖的不一致行为。

### 11.2 控制措施

1. 使用页面级 CSS，避免污染共享样式。
2. 对单任务卡引入新渲染 helper，减少对旧步骤列表 DOM 的直接复用。
3. 实时日志修复前先补诊断/回归测试，证明根因。
4. 代理策略在后端单点收口，并通过多任务类型测试锁定一致性。

---

## 12. 结论

本轮设计的核心不是“再涂一层 CSS”，而是对现有 Dashboard / 工作台做一次 **高亮控制台风格增强**，并借机把两个真正影响体验的点修透：

1. **实时日志仍不够实时**
2. **代理使用规则不统一且不透明**

最终落地方向已经固定为：

1. Dashboard 采用浅色高亮卡片与彩色数字标签。
2. 快捷动作采用按钮化布局。
3. 侧边栏折叠后只展示图标，按钮并入侧边栏本体。
4. 工作台日志区增高，单任务改为进度条模式。
5. 实时日志按根因修复，继续以 stream 实时事件为主路径。
6. 所有任务类型统一支持“是否使用代理”，并遵循：
   - 动态代理
   - 代理列表
   - 静态代理
   - 都不可用则任务创建后立即失败

这套方案在当前仓库架构内可渐进实现，不需要再次推翻上一轮实时流设计。
