# codex-console Workbench Flow 工作区 UI 重构设计

- 日期：2026-03-28
- 状态：Draft
- 目标读者：产品负责人、实施开发者、项目维护者
- 当前仓库：`/root/code-server/workspace/codex-console`

- 关系说明：本设计在 2026-03-24 版本基础上继续收敛，作为本轮“大范围 UI / UX 重构”的最新方案，后续计划与实现以本文为准。

## 1. 背景与问题定义

用户希望对当前 Web UI 做一次允许较大范围改造的整体重构，目标不是简单换皮，而是同时解决：

1. 全站专业感不足，视觉语言不统一。
2. 页面职责边界不清，工作流主线不够明确。
3. 多个页面存在结构、表格、表单、日志、状态表达不一致的问题。
4. 壳层交互存在明显缺陷，包括：
   - 退出登录按钮位置不合理；
   - 主题切换按钮位置不合理；
   - 侧边栏折叠状态跨页不稳定，切页时会先展开再缩回；
   - 暗色主题首帧会先以亮色渲染，再闪到暗色。

本轮设计要把产品重新组织为一个围绕注册任务运转的工作台系统，而不是若干彼此松散的功能页集合。

---

## 2. 已确认的用户决策

本轮设计已经和用户逐步确认了以下结论：

1. **视觉主题**
   - 采用 **双主题并重**；
   - 亮色与暗色都必须是完整、专业、统一的体验，不接受“顺带支持暗色”。

2. **信息密度**
   - 采用 **平衡型工作台**；
   - 既保持专业感和效率，又保留足够留白、层级与可读性。

3. **重构幅度**
   - 允许 **较大幅度重构工作流**；
   - 允许重组导航结构、页面分组和主次关系。

4. **产品主方向**
   - 采用 **Workbench Flow**；
   - 核心主线为：**任务发起 → 运行中 → 结果复盘**。

5. **主中心模块**
   - **注册工作台** 是整个产品的主中心。

6. **首页定位**
   - 登录后默认先进入 **总览页**，不是直接进入注册工作台；
   - 总览页是启动台和判断页，不是纯展示页。

7. **注册工作台定位**
   - 注册工作台偏 **专家控制台**；
   - 高效、直接、强掌控，不走向导式弱引导路线。

8. **注册工作台形态**
   - 采用 **主页面 + 可切换运行视图**；
   - 统一在一个主模块中承载：
     - 配置；
     - 运行中；
     - 最近结果。

9. **壳层交互修正**
   - 退出登录移到 **侧边栏左下角 / 底部账户区**；
   - 主题切换移到 **页头右上角**；
   - 折叠态必须跨页稳定持久；
   - 主题必须首帧恢复，避免闪烁。

## 3. 设计目标

### 3.1 本轮必须达成

1. 建立统一、专业、可扩展的工作区壳层。
2. 让全站信息架构围绕注册任务主线重组。
3. 建立统一视觉系统与双主题 token。
4. 统一表格、筛选栏、工作台、日志、状态标签、空态和抽屉/模态的组件语言。
5. 修正当前壳层交互中的跳动、闪烁和位置不合理问题。
6. 在不重写后端业务系统的前提下，让前端体验明显升级。

### 3.2 非目标

本轮不包含：

1. 前后端分离重建；
2. 引入 React/Vue 等新前端框架；
3. 重写现有后端 API；
4. 对注册、账号、调度业务流程做后端架构级改造；
5. 为了视觉改造而改变核心业务规则。

---

## 4. 总体设计结论

本轮采用的总体方案是：

> **Overview Hub + Workbench Flow + Dedicated Run Center**

也就是：

1. **总览页** 负责启动、判断和异常提醒；
2. **注册工作台** 负责发起任务与专家级控制；
3. **运行中心** 负责持续观察、日志、控制与状态聚合；
4. **账号资产 / 复盘 / 自动化与配置** 作为支撑域承接沉淀能力。

这套方案兼顾：

1. 首页总览的清晰入口感；
2. 注册工作台作为主中心的强定位；
3. 运行态作为一等能力被提升；
4. 页面之间职责更清楚，后续扩展更稳定。

## 5. 新的信息架构

### 5.1 一级导航

一级导航重组为以下结构：

1. **总览**
   - 控制台总览

2. **执行**
   - 注册工作台
   - 运行中心
   - 账号资产

3. **复盘**
   - 实验复盘

4. **支撑**
   - 自动化与配置

### 5.2 页面域说明

#### A. 总览页

定位为启动台，而不是纯统计页。

主要职责：

1. 展示系统健康、运行中任务、关键异常；
2. 展示最近任务、最近批次和待处理问题；
3. 提供进入注册工作台、运行中心、复盘页的高频入口。

#### B. 注册工作台

定位为产品主中心。

主要职责：

1. 发起注册任务；
2. 承载专家级参数配置；
3. 提供运行中视图和最近结果视图切换；
4. 以“配置 / 运行中 / 最近结果”组织核心内容。

#### C. 运行中心

这是本轮新增的核心页面域。

主要职责：

1. 聚合所有运行中、排队中、最近完成任务；
2. 统一呈现实时日志、关键事件、进度状态；
3. 统一支持停止、重试、跳转详情等控制动作。

数据与上下文原则：

1. 运行中心优先复用当前已有的注册任务、实时日志、计划运行记录相关 API 与事件流；
2. 运行中心是“统一观察与控制视图”，不是新的独立任务上下文；
3. 从注册工作台跳转到运行中心时，任务身份、日志来源和可控制动作必须保持一致，不允许出现“工作台里看到的是一套状态，运行中心里又是另一套状态”；
4. 运行中心中的控制动作必须明确区分：
   - 只影响当前选中任务；
   - 影响整个批次；
   - 影响调度/自动化任务。

#### D. 账号资产

账号管理从“第二工作台”改为“资产沉淀页”。

主要职责：

1. 高质量筛选和批量操作；
2. 账号状态治理、上传、订阅检测、Token 维护；
3. 详情抽屉式查看与操作。

#### E. 实验复盘

把“注册实验”和“批次统计”收拢到同一复盘域。

主要职责：

1. 实验对比；
2. 批次详情；
3. 趋势与结果分析。

#### F. 自动化与配置

把定时任务、邮箱服务、系统设置收拢为支撑域。

主要职责：

1. 自动化任务管理；
2. 邮箱、代理、上传与系统配置；
3. 按二级导航或标签管理复杂设置，而不是继续做超长拼接表单页。

## 6. 视觉系统

### 6.1 视觉语言

推荐视觉语言：

1. **Indigo + Slate** 作为品牌骨架；
2. **Amber** 作为强调/待处理/提醒色；
3. 避免 emoji 作为结构图标；
4. 避免大面积花哨玻璃化、彩虹渐变和装饰性拟物。

核心目标：

1. 专业；
2. 稳定；
3. 技术感；
4. 高一致性；
5. 在双主题下都保持同样清晰的层级。

### 6.2 双主题策略

#### 亮色主题：Clear Workbench

特征：

1. 背景清晰、可信；
2. 卡片与页面层级明确；
3. 更适合白天与长时间操作。

#### 暗色主题：Night Operations

特征：

1. 冷静、专业；
2. 日志、运行态、状态信号更突出；
3. 适合长时间监控与夜间使用。

要求：

1. 不是单纯反色；
2. 两套主题共享同一套层级规则、组件结构和状态系统；
3. 文本、边框、焦点、状态对比度都必须独立验证。

### 6.3 字体建议

推荐优先级：

1. UI 正文字体：`Inter` / `Noto Sans SC`
2. 日志、关键数据、代码样式：局部使用等宽字体，如 `Fira Code` / `JetBrains Mono`

原则：

1. 中文可读性优先；
2. 不使用过强风格化标题字体；
3. 页面标题、表格、表单、日志之间用字重与字号建立层级，而不是依赖装饰。

## 7. 壳层布局与全局交互

### 7.1 顶层结构

全局壳层统一为：

1. 左侧固定工作区侧边栏；
2. 右侧内容主区；
3. 页面顶部统一页头区域；
4. 工作区内所有页面复用同一壳层。

### 7.2 退出登录位置

退出登录必须：

1. 从页头移除；
2. 固定在侧边栏底部账户区；
3. 成为稳定、可预期的全局动作。

原因：

1. 退出不是当前页面主操作；
2. 顶部主操作位应留给页面级动作；
3. 放在侧边栏底部更符合工作区产品心智。

### 7.3 主题切换位置

主题切换必须：

1. 从侧边栏移出；
2. 固定在右上角页头操作区；
3. 与显示偏好、页头动作保持同一区域心智。

### 7.4 折叠态持久化规则

侧边栏折叠必须满足：

1. 折叠是一个持久化的全局状态；
2. 切页后必须直接以折叠态首帧呈现；
3. 用户不主动展开时，系统不能自己先展开再收回。

### 7.5 主题首帧规则

主题恢复必须：

1. 在首帧绘制前应用；
2. 避免暗色主题先亮后暗；
3. 避免布局与主题状态在 `DOMContentLoaded` 之后才补丁式恢复。

### 7.6 图标规则

1. 结构图标统一使用 SVG / 向量图标族；
2. 禁止用 emoji 承担导航、系统按钮、状态控制等结构性图标职责；
3. 只有业务内容本身需要时才允许 emoji 作为内容元素，而非系统控件。

## 8. 页面级布局方案

### 8.1 总览页

推荐布局：

1. 顶部：页面标题、摘要、副标题、关键入口；
2. 第一行：系统状态、运行中任务、异常、关键指标卡；
3. 第二行：最近任务 / 最近批次；
4. 侧列：进入注册工作台、运行中心、复盘页的快捷入口与提醒。

### 8.2 注册工作台

推荐布局：

1. 顶部统一工作台切换：
   - 配置
   - 运行中
   - 最近结果
2. 配置视图：
   - 左侧：参数配置与高级控制；
   - 右侧：智能摘要、预检查、风险提示、启动按钮。
3. 运行中视图：
   - 主日志流；
   - 任务进度卡；
   - 关键事件与控制动作。
4. 最近结果视图：
   - 最近批次结果；
   - 成败摘要；
   - 快速跳转到账号资产或复盘域。

### 8.3 运行中心

推荐布局：

1. 顶部：全局运行摘要与筛选；
2. 主区：运行队列 / 当前任务 / 最近完成；
3. 侧区：详细日志或任务详情；
4. 支持统一的控制动作：
   - 停止；
   - 重试；
   - 跳转详情；
   - 查看完整日志。

### 8.4 账号资产

推荐布局：

1. 顶部：资产指标卡与筛选栏；
2. 中部：统一数据表格；
3. 右侧或抽屉：账号详情、Token、订阅、上传状态；
4. 顶部工具栏：批量刷新、验证、上传、导出、删除等统一批量动作。

### 8.5 实验复盘

推荐布局：

1. 顶部：复盘页头与视图切换；
2. 主体按以下子域组织：
   - 实验；
   - 批次；
   - 趋势。
3. 分析卡、趋势面板、详情表格保持统一组件语言。

### 8.6 自动化与配置

推荐布局：

1. 定时任务独立成自动化子模块；
2. 邮箱、代理、上传、系统设置改成更清晰的二级导航或标签；
3. 超长单页设置拆成结构清晰的分组面板；
4. 所有配置操作都要具备清晰的保存、测试、反馈状态。

## 9. 组件系统基线

本轮需要统一的核心组件包括：

1. **Page Header**
   - 标题
   - 副标题
   - 面包屑 / 返回
   - 页头主操作

2. **Workbench Tabs**
   - 配置
   - 运行中
   - 最近结果

3. **Filter Bar**
   - 筛选控件
   - 搜索框
   - 批量操作
   - 重置与刷新

4. **Data Table**
   - 表头
   - 批量选择
   - 排序/筛选语义
   - 分页
   - 空态
   - 错误态

5. **Stat Card**
   - 指标值
   - 趋势/说明
   - 状态色

6. **Status Badge**
   - success
   - warning
   - error
   - neutral
   - active

7. **Log Panel**
   - 日志头
   - 自动滚动
   - 复制 / 清空 / 跳转
   - 加载中 / 暂无日志 / 错误态

8. **Drawer / Modal**
   - 账号详情
   - 服务选择
   - 配置确认
   - 危险操作确认

9. **Empty / Loading / Error State**
   - skeleton
   - inline error
   - retry
   - explanation text

## 10. 交互规范

### 10.1 加载反馈

所有主要异步操作必须具备显式反馈：

1. 页面初始加载；
2. 表格刷新；
3. 日志加载；
4. 表单提交；
5. 批量操作。

禁止“点击后无反馈”。

### 10.2 错误反馈

错误不能只依赖 toast。

必须同时具备：

1. 就地错误提示；
2. 必要时的重试入口；
3. 对应区域的状态更新。

### 10.3 空态

空态统一组件化，不再每页各写一套。

必须区分：

1. 暂无数据；
2. 正在加载；
3. 加载失败；
4. 无匹配筛选结果。

### 10.4 表格与批量操作

要求：

1. 表格头、行高、分页、空态统一；
2. 批量操作按钮文案与状态统一；
3. 危险动作有清晰确认；
4. 批量操作期间有 busy 态。

### 10.5 模态与抽屉

要求：

1. 键盘可达；
2. 焦点进入与返回正确；
3. `Esc` 行为一致；
4. 危险动作默认焦点不落在“确认”。

## 11. 可访问性与质量要求

本轮必须解决以下质量问题：

1. 焦点态必须可见；
2. 所有图标按钮必须有可读名称；
3. 文本对比度满足基本要求；
4. 不能只依赖颜色传达状态；
5. 错误信息要可被辅助技术感知；
6. 宽表格在小屏下有合理退化策略；
7. 双主题都必须单独验证，而不是只验证一套。

推荐的最低验证标准：

1. 常规文本对比度不低于 **4.5:1**；
2. 大字号文本、状态徽标中的主要文字不低于 **3:1**；
3. 图标按钮的可点击区域不小于 **44×44 px**；
4. 侧边栏折叠状态与主题状态必须在页面首帧前恢复，避免肉眼可见的闪烁与跳变；
5. 暗色主题切换或刷新时，不应出现完整一帧以上的亮色壳层闪现。

## 12. 当前代码约束与实现边界

本轮设计默认基于当前技术栈实现：

1. 模板层：`templates/*.html`
2. 公共壳层：
   - `templates/_workspace_base.html`
   - `templates/_workspace_sidebar.html`
   - `src/web/page_shell.py`
3. 公共样式与交互：
   - `static/css/style.css`
   - `static/js/workspace.js`
   - `static/js/utils.js`
4. 页面级样式与交互：
   - `static/css/dashboard_page.css`
   - `static/css/registration_workbench.css`
   - `static/css/realtime_log_console.css`
   - `static/js/*.js`

实现时允许：

1. 重构模板结构；
2. 重组公共 CSS token；
3. 抽离重复页面结构；
4. 调整导航和页面映射；
5. 对页面 JS 做必要的 DOM 适配与状态恢复优化。

实现时不应：

1. 先引入新框架再开始重构；
2. 因为 UI 设计而扩大到后端业务重写；
3. 把范围发散到非本轮目标功能。

## 13. 验收标准

本轮设计完成后，至少应满足：

1. 用户进入系统后，能明确感知“总览页 → 注册工作台 → 运行中心”的主路径。
2. 页面视觉系统高度统一，不再出现明显的拼贴感和风格漂移。
3. 退出登录位置、主题切换位置符合本设计约定。
4. 侧边栏折叠状态跨页稳定，不再出现先展开再缩回。
5. 暗色主题首帧不再闪烁。
6. 结构性 emoji 图标被清理，替换为统一图标系统。
7. 注册工作台、账号资产、运行中心、复盘页、自动化与配置页职责清晰。
8. 表格、筛选栏、日志面板、状态标签、空态、模态/抽屉都进入统一组件体系。
9. 从注册工作台跳转到运行中心后，任务状态、日志来源和控制动作语义保持一致。

---

## 14. 结论

本轮不是一次“美化样式”工作，而是一次**工作区产品重组**。

设计定稿后的产品骨架应为：

> **总览 → 注册工作台 → 运行中心 → 账号资产 / 实验复盘 / 自动化与配置**

同时以：

> **Indigo + Slate + Amber 的双主题工作台视觉系统**

作为统一视觉语言，并落实以下强制性交互修正：

1. 退出登录下沉到侧边栏底部；
2. 主题切换上移到页头右上角；
3. 折叠态跨页稳定；
4. 暗色主题首帧无闪烁。

只要实现严格遵循本设计，当前产品的专业感、一致性、工作流清晰度和可扩展性都会显著提升。
