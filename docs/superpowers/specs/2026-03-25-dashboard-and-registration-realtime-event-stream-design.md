# 首页与注册工作台实时事件流重设计

- 日期：2026-03-25
- 状态：Approved-for-planning
- 目标读者：产品负责人、实施开发者、项目维护者
- 当前仓库：`codex-console`

## 1. 背景

用户本轮明确提出两类问题：

1. 首页样式“很丑”，需要明显提升整体视觉质量。
2. 注册时日志没有实时展示，需要同步优化过程反馈体验。

在后续澄清中，用户进一步确认了如下选择：

1. 改造范围为 **首页 `/` + 注册工作台 `/registration-workbench`** 两页同时优化。
2. 整体风格选择 **现代数据看板**。
3. 工作台布局采用 **左侧配置约 1/3，右侧反馈约 2/3**。
4. 单个注册时，必须展示 **当前步骤进度**。
5. 批量注册时，必须展示 **注册目标数、成功数、失败数和进度条**。
6. 在实现路线对比中，用户最终选择 **方案 C：统一实时事件流 + 前端状态机**。

这意味着本轮设计不只是“改下 CSS”或“修一条 WebSocket”，而是要把页面视觉层级和注册过程实时反馈机制一起重做，但仍需控制在当前仓库技术栈与业务边界内完成，不做无关的大重构。

---

## 2. 当前问题分析

### 2.1 首页问题

当前首页已经改造成 Dashboard 入口，但仍然存在以下问题：

1. 视觉上更像功能容器，而不是真正的数据看板。
2. Hero、指标卡、最近活动、快捷入口之间层级不够强。
3. 全局状态摘要与下一步操作之间缺少明显节奏。
4. 页面虽然可用，但缺少“控制台总览”的第一眼辨识度。

### 2.2 注册工作台问题

当前注册工作台的问题更集中：

1. 配置区占比偏大，运行反馈区域不够突出。
2. 单注册步骤信息存在，但不够集中、稳定、直观。
3. 批量注册统计与日志反馈没有形成统一的高优先级反馈面板。
4. 页面在“配置”和“观察”两种任务之间边界不清楚。

### 2.3 实时日志问题

当前“注册日志不实时”的根因并不只是前端样式问题，而是实时链路存在结构性缺陷：

1. WebSocket 是主链路，但连接建立前已产生的日志可能存在补发不完整问题。
2. 降级轮询当前主要读取数据库中的 `task.logs`，而数据库日志采用缓冲后批量 `flush` 的方式写入。
3. 这导致一旦退回到轮询链路，日志展示天然滞后，不可能真正实时。
4. 单注册状态、步骤、日志、批量统计分别来自不同路径，前端需要拼接多个数据源，容易出现不同步。

结论是：**如果不统一实时模型，只做样式调整，用户的核心体验问题仍会反复出现。**

## 3. 方案对比与最终结论

本轮已讨论过三种方案：

### 3.1 方案 A：轻量修补

- 仅做页面美化。
- 局部修复 WebSocket / 轮询日志。
- 保持现有工作台结构基本不变。

优点是改动小、上线快；缺点是只能局部止痛，不能从根上解决实时反馈分裂问题。

### 3.2 方案 B：平衡升级

- 首页与工作台做结构级 UI 重排。
- 实时链路做增强，但仍保留现有多源拼接模式。

优点是成本适中；缺点是前端状态源仍不够统一，未来还会继续积累复杂度。

### 3.3 方案 C：统一实时事件流 + 前端状态机（已批准）

- 用统一事件流承载状态、步骤、日志、批量进度。
- 前端改为“snapshot + 增量事件”的单状态树渲染。
- 数据库只负责持久化，不再承担页面实时展示责任。
- 同时完成首页与注册工作台的视觉重设计。

**最终采用方案 C。**

原因如下：

1. 它能同时覆盖“样式丑”和“过程不实时”两类问题。
2. 它把单注册步骤、批量统计、日志流统一到一套实时模型里，减少前端拼接逻辑。
3. 它仍然可以在当前 FastAPI + Jinja2 + vanilla JS 架构上渐进落地，不需要前后端分离。

## 4. 本轮目标与非目标

### 4.1 本轮目标

本轮必须完成以下目标：

1. 将首页 `/` 提升为更成熟的现代数据看板。
2. 将注册工作台调整为 **1/3 配置区 + 2/3 反馈区**。
3. 单注册时提供稳定、清晰的 **当前步骤进度卡**。
4. 批量注册时提供稳定、清晰的 **目标数 / 成功数 / 失败数 / 进度条** 面板。
5. 建立统一的实时事件流，让日志、步骤、状态、批量统计统一更新。
6. 让 WebSocket 断线、页面切后台、轮询降级等场景下仍能保持正确的实时反馈。

### 4.2 非目标

本轮不包含以下内容：

1. 迁移到 React / Vue 或前后端分离。
2. 重写现有注册、账号、定时任务后端业务逻辑。
3. 引入消息队列、Redis Stream、Kafka 等额外基础设施作为前置条件。
4. 为所有历史页面统一接入事件流；本轮事件流仅覆盖注册工作台主路径。
5. 引入新的设计系统库或大型图表依赖。

## 5. 整体架构设计

### 5.1 核心思路

本轮将现有“状态、步骤、日志、批量统计分别广播 / 轮询 / 落库”的模式，重构为：

1. **后端统一实时事件中枢**：负责维护单任务与批任务的实时状态快照和事件缓冲。
2. **前端统一状态树**：页面先加载一个 snapshot，再连续消费增量事件。
3. **数据库持久化与实时展示解耦**：数据库仍保存历史日志和任务结果，但 UI 的实时性不依赖数据库 flush。

### 5.2 设计原则

1. **实时优先，落库异步**：用户看到的实时状态永远以事件流为准。
2. **单一数据源**：页面 UI 不再混用多条数据通道拼接状态。
3. **渐进改造**：在保留现有路由和模板结构的前提下升级 TaskManager 与页面 JS。
4. **可恢复**：断线、切后台、重连时能按序恢复，避免日志丢失与状态回跳。

### 5.3 架构示意

```text
RegistrationEngine / RegistrationService / BatchRegistrationService
                │
                ▼
        TaskManager 事件中枢
      ├─ 实时快照（task / batch）
      ├─ 事件缓冲区（按 stream + seq）
      ├─ WebSocket 广播
      └─ 增量补偿查询
                │
        ┌───────┴────────┐
        ▼                ▼
 snapshot REST      WebSocket / events REST
        │                │
        └───────┬────────┘
                ▼
         前端状态树 reducer
      ├─ 单注册步骤卡
      ├─ 批量统计卡
      └─ 实时日志流
```

## 6. 统一事件模型设计

### 6.1 事件外层结构

所有实时消息统一采用如下结构：

```json
{
  "seq": 128,
  "stream": "task:3f0c9f...",
  "kind": "log_appended",
  "timestamp": "2026-03-25T13:20:00Z",
  "payload": {}
}
```

字段定义如下：

1. `seq`：单个 stream 内的严格递增序号，用于去重、补发、断线恢复。
2. `stream`：流标识，格式为：
   - 单任务：`task:<task_uuid>`
   - 批任务：`batch:<batch_id>`
3. `kind`：事件类型。
4. `timestamp`：服务端生成时间。
5. `payload`：业务负载。

### 6.2 事件类型

本轮控制在以下 6 类：

1. `snapshot`
2. `task_status_changed`
3. `task_step_updated`
4. `batch_progress_updated`
5. `log_appended`
6. `stream_closed`

这样既足够覆盖本轮需求，又不会把事件类型拆得过细。

### 6.3 snapshot 结构

单任务 snapshot 建议至少包含：

1. `task`：任务基础状态与关键信息。
2. `current_step`：当前步骤摘要。
3. `steps`：完整步骤列表或最近步骤列表。
4. `logs_tail`：最近日志尾部，用于首次进入页面时显示上下文。
5. `connection_hint`：可选，指示当前流是否仍处于活跃态。

批量 snapshot 建议至少包含：

1. `batch`：批次状态。
2. `target_total` / `completed` / `success` / `failed` / `remaining`。
3. `is_unlimited` / `consecutive_failures` / `max_consecutive_failures`。
4. `domain_stats`：若本轮已有统计数据则一并给出。
5. `logs_tail`：最近日志尾部。

### 6.4 seq 语义

1. `seq` 只在单个 stream 内递增，不要求跨 stream 全局有序。
2. 前端仅接受 `seq > lastSeq` 的事件。
3. 小于等于 `lastSeq` 的事件直接丢弃，以防重连后重复消费。

## 7. 后端设计

### 7.1 TaskManager 升级为事件中枢

当前 `TaskManager` 已经负责：

1. 任务状态内存态。
2. 任务步骤快照。
3. 单任务 / 批任务日志队列。
4. WebSocket 广播。

本轮在此基础上扩展，而不是引入全新中间层。新增职责包括：

1. 为每个 task / batch 维护 `seq` 计数器。
2. 为每个 stream 维护事件缓冲区。
3. 提供统一的 `append_event()` 能力。
4. 提供 `build_snapshot()`、`get_events_after()` 能力。
5. 让状态更新、步骤更新、日志追加、批量统计更新都先写入事件流，再由广播层分发。

### 7.2 建议新增的内存结构

建议在 `TaskManager` 内维护以下结构：

1. `stream_seq_counters: Dict[str, int]`
2. `stream_event_buffers: Dict[str, deque]`
3. `stream_snapshots: Dict[str, dict]`
4. `stream_locks: Dict[str, Lock]`

其中事件缓冲区使用有长度上限的 deque，避免内存无限增长。

### 7.3 事件缓冲策略

建议按 stream 保留最近一段事件窗口，例如：

1. 最近 500～2000 条事件；或
2. 最近 15～30 分钟的事件。

具体窗口大小可实现时根据日志密度调整，但必须满足：

1. 正常切后台 / 轻度断线能够补回。
2. 超过窗口则触发“重新拉 snapshot”。

### 7.4 统一快照构建

TaskManager 应能按 stream 构建当前快照：

1. 单任务快照来自：
   - `_task_status`
   - `_task_steps`
   - `_log_queues` 的 tail
2. 批任务快照来自：
   - `_batch_status`
   - `_batch_logs` 的 tail

快照构建不依赖数据库；数据库只用于历史详情与结果查询。

### 7.5 路由设计

建议新增统一实时路由，而不是继续扩散旧接口语义：

1. `GET /registration/streams/task/{task_uuid}/snapshot`
2. `GET /registration/streams/task/{task_uuid}/events?after_seq=<n>`
3. `GET /registration/streams/batch/{batch_id}/snapshot`
4. `GET /registration/streams/batch/{batch_id}/events?after_seq=<n>`
5. `WS /ws/task/{task_uuid}?after_seq=<n>`
6. `WS /ws/batch/{batch_id}?after_seq=<n>`

现有旧接口可以暂时保留，供过渡期或其他页面使用，但注册工作台切换到新接口。

### 7.6 事件写入点

#### 单任务

以下操作需要改为写入统一事件流：

1. `update_status()` → 触发 `task_status_changed`
2. `set_task_steps()` → 触发 `task_step_updated`
3. `add_log()` → 触发 `log_appended`
4. 任务结束 / 失败 / 取消 → 触发 `stream_closed`

#### 批任务

以下操作需要改为写入统一事件流：

1. `update_batch_status()` → 触发 `batch_progress_updated`
2. `add_batch_log()` → 触发 `log_appended`
3. 批任务结束 / 失败 / 取消 → 触发 `stream_closed`

### 7.7 数据库角色调整

数据库仍然保留：

1. 任务最终结果。
2. 历史日志。
3. 运行记录、批次统计、账号落库。

但数据库**不再作为实时 UI 的主数据源**。这意味着：

1. 即使日志仍采用批量 flush，也不影响实时展示。
2. 实时 UI 优先消费内存事件流。
3. 历史查询与刷新页面后的长周期回看，仍可回到数据库接口。

## 8. 前端设计

### 8.1 首页 `/` 结构

首页采用三层结构：

#### 第一层：Hero 总览区

1. 左侧一个强化视觉的 Hero 概览区，负责展示当前系统总览与一句状态摘要。
2. 右侧四张紧凑指标卡，展示：
   - 注册任务总数
   - 注册成功率
   - 账号总数 / 活跃数
   - 定时计划总数 / 启用数

#### 第二层：中部双栏信息区

1. 左栏：最近活动 / 最近关键结果。
2. 右栏：快捷入口 / 任务健康摘要。

#### 第三层：统一面板风格

所有模块采用统一 card 体系，强化留白、圆角、边框、阴影和标题层级，形成更稳定的 Dashboard 质感。

### 8.2 注册工作台 `/registration-workbench` 结构

工作台采用用户已确认的 **1/3 : 2/3** 布局。

#### 左侧 1/3：配置区

左侧保留“启动任务相关”配置：

1. 邮箱服务
2. 注册模式
3. 批量参数 / 并发参数
4. 自动上传设置
5. 开始 / 取消按钮

该区域的设计目标是：**紧凑但不拥挤，像控制面板而不是旧式表单堆叠。**

#### 右侧 2/3：反馈区

右侧反馈区固定为三层：

1. **单注册步骤进度卡**
   - 展示当前状态、当前步骤、耗时、邮箱、服务类型等关键信息。
2. **批量统计卡**
   - 展示目标数、完成数、成功数、失败数、剩余数、进度条。
   - 无限模式下展示已完成、成功、失败、连续失败与运行状态。
3. **实时日志流**
   - 采用深色终端风格。
   - 自动滚动。
   - 按级别区分颜色。
   - 显示连接状态（已连接 / 重连中 / 降级同步中）。

### 8.3 页面空态与模式切换

#### 无活动任务时

右侧展示空态，提示“启动任务后将看到步骤进度、批量统计和实时日志”。

#### 单任务运行时

1. 强调当前步骤卡。
2. 批量统计区域弱化或隐藏。
3. 日志区继续显示全部实时日志。

#### 批量任务运行时

1. 强调批量统计卡。
2. 单任务步骤卡只保留轻量摘要，避免界面过于拥挤。
3. 详细过程主要进入日志区。

### 8.4 前端状态树

前端工作台改为维护统一状态对象，例如：

```js
{
  streamId,
  mode,
  lastSeq,
  task: {},
  batch: {},
  currentStep: null,
  steps: [],
  logs: [],
  connection: {
    status: 'connected' | 'reconnecting' | 'polling'
  }
}
```

所有 UI 都从这棵状态树派生，不再由多个接口分别直接改 DOM。

### 8.5 reducer 驱动渲染

前端使用一个轻量 reducer / dispatcher 模式处理事件：

1. `snapshot`：初始化整棵状态树。
2. `task_status_changed`：更新任务状态。
3. `task_step_updated`：更新当前步骤与步骤列表。
4. `batch_progress_updated`：更新批量统计卡。
5. `log_appended`：向日志数组追加并触发终端区更新。
6. `stream_closed`：停止 loading，冻结状态并结束重连。

这样可以避免旧页面中“日志更新到了，但步骤卡没动；批量数字变了，但进度条没刷”的分裂体验。

## 9. 数据流与连接恢复设计

### 9.1 初次进入流

单任务 / 批任务统一采用如下流程：

1. 前端拿到 `task_uuid` 或 `batch_id`。
2. 请求一次 `snapshot`。
3. 保存 `lastSeq`。
4. 建立 WebSocket，并带 `after_seq=lastSeq`。
5. 服务端若有缺失事件先补发，再进入实时推送。

### 9.2 WebSocket 主链路

WebSocket 是首选主链路，承担：

1. 实时日志推送。
2. 步骤变更推送。
3. 批量统计变更推送。
4. 任务结束收口通知。

### 9.3 降级补偿链路

当 WebSocket 断开时：

1. 前端保留 `lastSeq`。
2. 临时轮询 `events?after_seq=<lastSeq>`。
3. 若补偿成功，则继续更新页面。
4. WebSocket 恢复后继续从最新 `lastSeq` 接续。

### 9.4 全量重同步

如果增量事件缓冲区不足以覆盖断线窗口：

1. 服务端返回“需要重新同步”的信号。
2. 前端自动重新拉 `snapshot`。
3. 用新 snapshot 重建状态树。
4. 再继续订阅后续事件。

恢复优先级为：

```text
WebSocket 增量恢复 > REST events 补偿 > snapshot 全量重建
```

## 10. 错误处理设计

### 10.1 业务错误

如邮箱创建失败、验证码超时、OAuth 失败、注册失败：

1. 实时日志继续写入。
2. 单任务发 `task_status_changed`。
3. 最终发 `stream_closed`。
4. 单注册步骤卡直接显示失败步骤与错误摘要。
5. 批量任务仅增加失败数，不让整个工作台进入不可用状态。

### 10.2 连接错误

如 WebSocket 断开、网络抖动、页面切后台后失联：

1. UI 顶部显示连接状态。
2. 自动进行指数退避重连。
3. 重连期间切换到 events 补偿轮询。
4. 恢复后回到实时模式。

### 10.3 事件窗口过期

如果 `after_seq` 已早于服务端保留窗口：

1. 服务端显式返回“snapshot required”。
2. 前端自动全量同步。
3. 不让页面长期停留在错误状态。

### 10.4 落库失败

如果数据库日志 flush 或结果持久化失败：

1. 不影响实时 UI 展示。
2. 服务端记录错误日志。
3. 页面只在必要时提示“历史记录可能不完整”。

核心原则是：**数据库故障不应直接摧毁实时过程反馈。**

## 11. 测试策略

### 11.1 后端测试

必须补齐以下关键测试：

1. 事件 `seq` 按 stream 单调递增。
2. 初次连接可获取 snapshot，并能继续消费增量事件。
3. `after_seq` 补偿可正确返回缺失事件。
4. 事件缓冲不足时可返回“需要重新同步”。
5. 即使数据库日志未 flush，内存事件流仍能实时推送日志。
6. 单任务状态、步骤、日志更新均能正确生成事件。
7. 批量统计更新能生成统一事件并广播。

### 11.2 前端测试

继续使用现有 JS harness 方式，重点覆盖：

1. `snapshot` 初始化页面。
2. 单注册步骤卡渲染。
3. 批量统计卡渲染。
4. `log_appended` 追加、去重、自动滚动。
5. `seq` 去重与防乱序处理。
6. WebSocket 断开、轮询补偿、恢复连接三种状态切换。

### 11.3 集成测试

补两类主路径集成测试：

1. **单注册流程**
   - 启动任务
   - 推进步骤
   - 实时追加日志
   - 任务成功 / 失败收口
2. **批量注册流程**
   - 目标数 / 成功数 / 失败数 / 进度条实时更新
   - 日志持续追加
   - 最终状态正确冻结

## 12. 渐进迁移策略

本轮虽然采用方案 C，但仍按渐进迁移实施，而不是一次性推倒重来。

### 12.1 推荐迁移顺序

1. 先增强 `TaskManager`，加入事件缓冲、snapshot 与 `after_seq` 能力。
2. 再扩展实时路由与 WebSocket 协议。
3. 然后改造注册工作台前端为“状态树 + reducer + 新流接口”。
4. 最后清理旧轮询、旧多源拼接逻辑，并完成首页样式重设计。

### 12.2 兼容策略

过渡期允许保留：

1. 旧的 `/registration/tasks/{task_uuid}` 详情接口。
2. 旧的 `/registration/tasks/{task_uuid}/logs` 接口。
3. 旧批任务状态接口。

但注册工作台页面切换到新实时协议后，旧接口仅作为兼容或其他页面使用，不再作为主链路。

## 13. 风险与缓解

### 13.1 风险：事件流改动触及注册主路径

缓解：

1. 保留旧接口。
2. 使用渐进切换。
3. 用回归测试保护单注册与批量注册主路径。

### 13.2 风险：前端 reducer 改造引入页面状态 bug

缓解：

1. 用 JS harness 固化关键事件序列。
2. 先收敛为少量事件类型。
3. 所有 DOM 更新统一走 render 层。

### 13.3 风险：事件缓冲窗口过小导致频繁全量同步

缓解：

1. 为日志高频流预留足够窗口。
2. 首轮上线时增加观测日志。
3. 允许根据真实运行密度调节 buffer 上限。

---

## 14. 验收标准

本轮设计的实现完成后，应满足以下验收标准：

1. 首页视觉明显提升，具备现代数据看板层级感。
2. 注册工作台稳定呈现 **1/3 配置 + 2/3 反馈** 布局。
3. 单注册运行时，用户可以明确看到当前步骤、步骤状态和实时日志。
4. 批量注册运行时，用户可以明确看到目标数、成功数、失败数和进度条。
5. 日志实时显示不再依赖数据库 flush 才出现。
6. 页面切后台、WebSocket 断开或短时网络波动后，仍能恢复正确状态。
7. 前端不会出现日志重复、顺序错乱、批量数字回跳等明显同步问题。

---

## 15. 设计结论

本轮已确认采用 **“首页 + 注册工作台视觉重设计” 与 “统一实时事件流 + 前端状态机”** 的组合方案。

该方案的核心价值在于：

1. 把首页真正提升为控制台总览。
2. 把注册工作台明确拆成“配置”与“反馈”两大职责区域。
3. 把日志、步骤、批量统计统一到一套实时模型中。
4. 让实时体验摆脱数据库 flush 的天然延迟。
5. 在当前技术栈上渐进落地，不引入不必要的大框架迁移。

该设计已具备进入 implementation plan 的条件。
