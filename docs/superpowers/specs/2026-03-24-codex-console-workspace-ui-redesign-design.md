# codex-console 工作区化 UI 重设计

- 日期：2026-03-24
- 状态：Approved-for-planning
- 目标读者：产品负责人、实施开发者、项目维护者
- 当前仓库：`/root/code-server/workspace/codex-console`
- 参考项目：`/root/project/chatgpt-register7`

## 1. 背景

用户希望参考 `chatgpt-register7` 项目的整体设计，对当前 `codex-console` 做两件事：

1. 详细分析参考项目的整体设计，并与当前项目做对比。
2. 将当前项目按参考项目喜欢的前端样式与交互模式进行改造。

本轮已确认的用户选择如下：

1. 改造范围为**全站统一改造**，不是只改首页。
2. 改造深度为**视觉 + 页面布局重组**，不做前后端重写。
3. 全站壳层采用 **Sidebar Workspace** 方案。
4. 侧边栏必须支持**展开 / 收起**。
5. 一级导航采用**按工作流分组**：
   - 总览
   - 执行
   - 复盘
   - 配置
6. 视觉风格采用**高度贴近参考项目**的暖色监控台风格。
7. 当前首页 `/` 统一改成 **Dashboard 总览**；原首页注册操作迁移到新的 **`/registration-workbench`**。

本设计目标不是把 `codex-console` 变成 `chatgpt-register7` 的逐像素复刻，而是提取后者在**视觉语言、信息密度、总览层级、监控台氛围**上的优点，嫁接到当前这个功能更完整的多页面系统中。

## 2. 参考项目整体设计分析

### 2.1 项目结构侧重点

参考项目 `chatgpt-register7` 的前端与运行形态有如下特征：

1. 以统一入口 `main.py` 承载 Dashboard 与后台任务。
2. 主页面集中在 `dashboard/zhuce6.html`，属于**单页监控大盘**思路。
3. 页面内容围绕运行态、失败信号、任务健康、近期记录、代理池、运行配置展开。
4. 强调“**总览优先**”，操作入口相对弱化。

这意味着参考项目不是典型的 CRUD 后台，而是一个运营 / 监控取向很强的控制台。

### 2.2 视觉设计特征

参考项目页面最值得借鉴的视觉特征有：

1. **暖米色 / 棕橙色基底**
   - 背景采用暖色渐变；
   - 卡片为浅暖白；
   - 边框与阴影柔和，形成低压迫感的监控台气质。
2. **卡片体系非常统一**
   - 所有信息块都放在同一种 card 体系里；
   - Hero 指标卡顶部使用细强调条；
   - 面板头与面板体分层清晰。
3. **信息密度高，但可读性仍然强**
   - 指标、状态、日志、列表、配置都在同一视觉语言下；
   - 通过字体层级、边框轻重、区域切分来避免混乱。
4. **视觉辨识度强**
   - 它不像常见后台模板，而更像专用运营控制台。

### 2.3 交互模式特征

参考项目的交互模式也有明显特点：

1. 首页默认是**驾驶舱**，不是配置页或表单页。
2. 用户进入后先理解“现在发生了什么”，再决定“下一步做什么”。
3. 多数模块采用**摘要优先、细节后钻取**的浏览方式。
4. 操作路径短，强调“快速判断系统状态”。

### 2.4 架构层面的启发

虽然参考项目是较轻量的一体化页面，但它给当前项目的启发很明确：

1. **总览视角要前置**。
2. **视觉系统要统一**，不能一页一个样。
3. **操作页也应保留监控台式的状态反馈**，不能只有表单。
4. **页面之间要有同一个工作区外壳**，而不是单独拼接。

## 3. 当前项目现状分析

### 3.1 当前前端结构

当前 `codex-console` 是一个 FastAPI + Jinja2 + vanilla JS 的多页面 Web UI：

1. 模板目录：`templates/`
2. 样式目录：`static/css/style.css`
3. 交互脚本目录：`static/js/*.js`
4. 页面路由集中在 `src/web/app.py`

当前主要页面包括：

1. `index.html`：注册页
2. `accounts.html`：账号管理
3. `email_services.html`：邮箱服务
4. `scheduled_tasks.html`：定时任务
5. `settings.html`：设置
6. `payment.html`：支付
7. `registration_experiments.html`：实验对比
8. `registration_batch_stats.html`：批次统计
9. `login.html`：登录

### 3.2 当前前端优点

当前项目已经具备以下强项：

1. 功能覆盖完整，远多于参考项目单页大盘。
2. 已有一定的现代化样式基础，支持主题切换。
3. 页面 JS 已经按页面拆分，不是单个巨大脚本。
4. 后端 API 丰富，支持注册、批量任务、账号管理、复盘与配置。

### 3.3 当前前端问题

相对于用户喜欢的参考项目风格，当前项目主要问题不是“功能少”，而是“整体感弱”：

1. 当前首页是**注册操作页**，不是总览 Dashboard。
2. 页面之间虽然共用部分样式，但**工作区外壳不统一**。
3. 导航是传统顶栏模式，不像一个稳定的多模块控制台。
4. 视觉语言仍偏“通用后台 + 表单页”，监控台氛围不够强。
5. 部分页面信息层级靠内容堆叠完成，而不是靠统一的页面骨架完成。

### 3.4 当前项目与参考项目的关键差异

| 维度 | 参考项目 `chatgpt-register7` | 当前项目 `codex-console` |
|---|---|---|
| 产品形态 | 单页监控大盘为主 | 多页面操作台 |
| 首页角色 | 总览驾驶舱 | 注册表单页 |
| 视觉气质 | 暖色运营监控台 | 现代后台 / 功能页 |
| 导航结构 | 首页主导、入口收敛 | 顶部平铺多页面 |
| 信息组织 | 摘要优先 | 功能优先 |
| 功能范围 | 较聚焦 | 更完整、更复杂 |

结论是：**当前项目最值得改的不是业务层，而是“前端壳层 + 首页定位 + 全站层级统一”。**

## 4. 值得借鉴的点与不应照搬的点

### 4.1 值得借鉴

本次设计明确借鉴以下内容：

1. 暖米色背景与浅暖白卡片体系。
2. Hero 指标卡 + 主内容面板 + 辅助侧栏的信息组织方式。
3. 顶部轻量 Header + 高信息密度面板风格。
4. 监控台式的状态优先逻辑。
5. 摘要先行、明细后钻取的浏览节奏。

### 4.2 不应照搬

以下内容不直接照搬：

1. 不把当前多页面系统强行压成单页。
2. 不丢掉当前复杂业务能力以换视觉一致性。
3. 不把当前项目退化成“只能看状态、不方便操作”的监控看板。
4. 不推翻当前 FastAPI + Jinja2 + vanilla JS 技术栈。

因此本次选择的是**借鉴其产品气质和信息结构，而不是照抄其工程形态**。

## 5. 已确认范围

### 5.1 本轮目标

本轮 UI 重设计必须完成以下目标：

1. 建立统一的工作区壳层。
2. 将首页 `/` 改造成 Dashboard 总览。
3. 将注册操作迁移到独立的注册工作台。
4. 为所有主要页面接入统一导航、统一页面头、统一卡片体系。
5. 让视觉气质高度贴近参考项目。
6. 在不重写后端业务逻辑的前提下完成改造。

### 5.2 非目标

本轮不包含：

1. 前后端分离或迁移到 React / Vue。
2. 重写现有 API。
3. 大规模重构注册、账号、定时任务等后端业务流程。
4. 引入图表平台、设计系统库等新基础设施作为前置条件。
5. 对所有页面交互逻辑做彻底重写。

## 6. 推荐方案与理由

本轮采用的已批准方案为：**统一壳层 + 页面重组**。

### 6.1 为什么不用“只换皮肤”

只换皮肤不能解决当前问题的根源：

1. 首页角色仍然错误。
2. 页面骨架不统一。
3. 各页面仍然像独立功能页，不像同一个工作区。

### 6.2 为什么不用“前端重建”

前端重建会带来不必要风险：

1. 当前项目模板和脚本已较多；
2. 现有功能密度高，回归成本大；
3. 用户当前诉求是“参考样式与交互模式改造”，不是“重写前端框架”。

### 6.3 方案结论

因此，本设计采用：

1. 保留现有 FastAPI 路由和大部分页面 JS。
2. 重构模板层与公共样式层。
3. 必要时对页面脚本做最小限度的 DOM 适配。
4. 通过新 Dashboard 与新 workspace shell 重建全站体验。

## 7. 新的信息架构

### 7.1 一级导航分组

全站导航按工作流重新分为四组：

1. **总览**
   - 控制台总览 Dashboard
2. **执行**
   - 注册工作台
   - 账号工作台
   - 定时任务
   - 支付操作
3. **复盘**
   - 实验对比
   - 批次统计
4. **配置**
   - 邮箱服务
   - 系统设置

### 7.2 导航设计原则

导航不再采用当前顶栏平铺方式，而改为：

1. 左侧固定窄图标轨道；
2. 右侧可展开 / 收起的分组侧边栏；
3. 当前页面的分组和条目高亮明确；
4. 折叠时保留图标轨道，不完全隐藏导航。

这样既符合用户选择的 Sidebar Workspace 方案，也能避免完全折叠后迷路。

## 9. 全站工作区壳层设计

### 9.1 统一壳层结构

所有主页面共用同一套 workspace shell：

1. **左侧导航区**
   - 固定窄图标轨道
   - 可折叠文字侧栏
2. **右侧内容区**
   - 页面头
   - 指标卡区（如适用）
   - 主内容面板
   - 辅助内容面板

### 9.2 侧边栏交互规则

侧边栏的行为定义如下：

1. 支持展开 / 收起切换。
2. 收起时仍保留图标轨道。
3. 展开状态保存在浏览器本地。
4. 页面切换后维持用户上次偏好。
5. 小屏下可退化为抽屉式，但仍尽量沿用同一视觉语言。

### 9.3 页面头统一规范

所有页面统一使用页面头，包含：

1. 面包屑；
2. 页面标题；
3. 一句副标题；
4. 右侧快捷操作按钮区。

这样可确保用户切到任何页面都立即理解：

1. 自己当前处于哪个工作流；
2. 当前页的主职责是什么；
3. 当前页最关键的操作是什么。

### 9.4 通用内容布局模式

本次只允许两种主布局模式：

1. **大主面板 + 右侧辅助面板**
2. **单列卡片栈**

避免不同页面各自发展出不同的骨架。

## 10. 统一视觉系统设计

### 10.1 视觉方向

视觉风格采用“高度贴近参考项目”的暖色运营台风格，核心特征如下：

1. 暖米色背景渐变；
2. 浅暖白卡片底；
3. 棕橙强调色；
4. 柔和边框与轻阴影；
5. 紧凑但不压抑的信息密度。

### 10.2 视觉 token 方向

建议建立统一的样式 token，包括：

1. 颜色：
   - 页面背景
   - 卡片背景
   - 边框色
   - 文字主次色
   - 强调色
   - 成功 / 警告 / 错误状态色
2. 间距：
   - 页面间距
   - 卡片内边距
   - 面板之间的 gap
3. 圆角：
   - 页面主卡片
   - 指标卡
   - 按钮
   - 表单控件
4. 阴影：
   - 常规 card shadow
   - Hero card shadow

### 10.3 通用组件视觉规范

统一组件应包括：

1. Hero 指标卡
2. 普通面板卡
3. 表格容器
4. 状态徽章
5. 工具栏按钮
6. 空状态 / 错误状态 / 加载状态

其中 Hero 指标卡沿用参考项目最有效的表达方式：

1. 顶部细强调条；
2. 大数字；
3. 次级说明文字。

## 11. 各页面落位设计

### 11.1 控制台总览 Dashboard

新首页承担总览职责，主要展示：

1. 注册总体状态与今日产出；
2. 账号池状态；
3. 当前活跃任务与定时任务健康；
4. 最近实验 / 批次摘要；
5. 最近异常信号、失败热点或关键提醒；
6. 到各工作台的快捷入口。

首页的目标不是提供全部操作，而是先回答：

1. 当前系统整体健康吗？
2. 哪个模块最值得我立刻关注？
3. 我应该从哪个工作台继续深入？

### 11.2 注册工作台

注册工作台承接原首页的核心能力，但布局重组为：

1. 左侧：注册配置与启动控制；
2. 中间：运行态、进度、日志、步骤瀑布；
3. 右侧：最近账号、辅助状态、快捷操作。

这使注册页仍然是强操作页，但也拥有监控台式状态反馈。

### 11.3 账号工作台

账号页改造成“指标 + 筛选 + 表格 + 批量动作”的资产工作台：

1. 顶部前置账号总量、状态分布、服务分布等指标；
2. 中间为筛选与搜索工具栏；
3. 主区域为表格与批量操作；
4. 详情抽屉或详情区保持现有能力即可，不要求重写交互模型。

### 11.4 定时任务 / 支付 / 配置页

这些页面不重写业务逻辑，只统一：

1. workspace shell；
2. 页面头；
3. 指标卡；
4. 面板层级；
5. 提示、空状态与错误态外观。

### 11.5 复盘页

实验对比与批次统计统一成“分析工作台”风格：

1. 先给摘要卡；
2. 再给对比区和明细区；
3. 统一图表 / 统计容器；
4. 提高复盘感，而不是普通列表页观感。

### 11.6 登录页与边缘状态页

登录页、无数据页、失败提示、空列表等边缘状态也接入同一视觉系统，避免主界面与边缘页面风格断裂。

## 12. 交互模式设计

### 12.1 摘要优先

所有核心页面都应遵循：

1. 先展示关键状态摘要；
2. 再给出操作或钻取入口；
3. 明细留在后方。

### 12.2 状态前置

像当前首页这种“先表单、后日志”的结构，不再作为全站默认思路。新设计要求：

1. 用户先能看见关键状态；
2. 再进入具体操作。

### 12.3 页面一致性

用户在任意页面都应看到相同的：

1. 导航位置；
2. 页面头结构；
3. 卡片语言；
4. 按钮样式；
5. 表格容器样式；
6. 提示反馈方式。

### 12.4 最小 JS 适配原则

页面改造过程中，优先通过模板结构和 class 命名兼容现有 JS；仅当旧脚本强依赖旧 DOM 时，再做最小必要的脚本适配。

## 13. 技术落地方式

### 13.1 总体原则

本次实施遵循：**重构模板层，不重写业务层。**

具体含义是：

1. 保留现有 FastAPI 路由与 API 层；
2. 保留大部分页面级 JS；
3. 重构模板组织方式；
4. 重构全局 CSS；
5. 补充统一的 shell 脚本与导航交互脚本；
6. 仅对必须适配的页面脚本做局部修改。

### 13.2 建议新增的前端结构

建议引入以下公共结构：

1. **workspace shell**
   - 导航数据
   - 页面布局骨架
   - 侧边栏折叠逻辑
2. **shared design tokens**
   - 统一颜色、间距、圆角、阴影
3. **shared UI blocks**
   - hero card
   - panel card
   - badge
   - toolbar
   - empty state
4. **page-level layout helpers**
   - dashboard layout
   - workbench layout
   - table / analysis layout

### 13.3 模板层改造方向

建议模板层从多个相互独立页面，收敛为：

1. 基础 layout 模板；
2. workspace shell 模板；
3. 页面内容块模板；
4. 必要的页面局部模板片段。

这样能降低未来页面继续分裂的概率。

---

## 14. 风险与控制策略

### 14.1 DOM 结构变动影响现有脚本

风险：

1. 现有 `static/js/*.js` 可能依赖某些固定 DOM id / class。

控制策略：

1. 优先保持关键 id 不变；
2. 若需要结构迁移，增加兼容层而不是大面积重写脚本；
3. 页面改造时逐页验证核心交互。

### 14.2 首页职责调整带来测试断裂

风险：

1. `/` 不再返回旧注册页，会影响已有测试与用户习惯。

控制策略：

1. 补充 `/` 的 Dashboard 页面测试；
2. 为 `/registration-workbench` 增加页面与静态资源测试；
3. 在导航中提供显式入口，避免功能“像被删掉”。

### 14.3 样式统一影响边缘页面

风险：

1. 边缘页可能接入不完整，造成主界面漂亮、登录页很旧的断层。

控制策略：

1. 登录页、空状态页、错误态也纳入本轮范围；
2. 统一由共享样式系统管理。

## 15. 测试与验证要求

### 15.1 页面级验证

至少应验证：

1. `/` 能正常渲染新 Dashboard；
2. `/registration-workbench` 能正常渲染注册工作台；
3. 其余主要页面仍可打开；
4. 页面都引用新的统一样式与脚本；
5. 页面导航高亮正确。

### 15.2 交互级验证

至少应验证：

1. 侧边栏展开 / 收起正常；
2. 折叠状态在刷新后仍能恢复；
3. 原有表单、按钮、表格、日志区域核心行为不失效；
4. 旧脚本在新 DOM 结构下仍能正常绑定。

### 15.3 回归验证

至少应保留并补充：

1. 静态资源版本相关测试；
2. 页面资产加载测试；
3. 首页与注册页路由测试；
4. 关键页面结构 smoke test。

## 16. 实施顺序建议

推荐按以下顺序实施：

1. 建立全局 workspace shell 与设计 token；
2. 改造首页 Dashboard；
3. 拆出注册工作台并迁移原首页操作能力；
4. 统一账号、定时任务、设置、邮箱服务页面；
5. 统一复盘页与登录页；
6. 最后清理旧导航和重复样式。

这一顺序的好处是：

1. 先建立全站骨架；
2. 再改两个最关键入口页；
3. 最后逐页接入统一系统。

## 17. 最终设计结论

本轮已批准的设计结论如下：

1. `codex-console` 将被改造成一个**统一的工作区式运营控制台**。
2. 视觉与交互模式将**高度贴近 `chatgpt-register7`** 的暖色监控台风格。
3. 全站采用**可折叠 Sidebar Workspace** 壳层。
4. 一级导航按**总览 / 执行 / 复盘 / 配置**分组。
5. 首页 `/` 改为 Dashboard，总览系统状态。
6. 注册能力迁移到 `/registration-workbench`。
7. 其余页面在保留现有业务能力的前提下，统一壳层、层级、卡片与交互规则。

一句话总结：

> 把当前功能完整但整体感不足的 `codex-console`，改造成一个外观与气质高度贴近参考项目、同时更适合多模块日常操作的统一工作区控制台。
